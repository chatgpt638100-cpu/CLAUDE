# Invitation Card Editor — Handoff

Offline Android invitation editor, Flutter. Clean Architecture, Riverpod,
GoRouter, GetIt, Hive.

Built against two specifications, both in the repository root:
`project-architecture.pdf` (layering, folder structure, dependency rationale)
and `invitation-editor-uiux-design.pdf` (screens, palette, accessibility
rules for a 50+ audience).

> **Status: never compiled.** Every line was written in an environment with
> no Dart toolchain and an egress proxy that blocks `pub.dev`,
> `storage.googleapis.com` and `github.com` downloads. The code is verified
> structurally, not by a compiler. Read "First build" before anything else.

## First build

```bash
cd invitation_editor
flutter pub get
flutter analyze
flutter run          # Android device, USB debugging enabled
```

`pubspec.lock` and the Gradle wrapper are generated by that first command —
both are correctly absent from git.

**Requires Flutter 3.27 or newer.** The code uses `Color.withValues()` and
`Color.toARGB32()` (3.27+) and `PopScope.onPopInvokedWithResult` (3.24+). On
an older SDK these produce a wall of errors before anything else.

## Architecture

Three layers per feature, dependencies pointing inward only.

```
lib/
├── main.dart                    entry: fonts offline, Hive, DI, theme, router
├── core/                        shared, belongs to no feature
│   ├── constants/               app_colors, app_text_styles, app_dimensions
│   ├── theme/                   app_theme (light + Warm Dark), app_fonts
│   ├── storage/                 local_storage (Hive boxes)
│   ├── errors/                  failures
│   ├── utils/                   app_paths, id_generator, date_formatting
│   ├── widgets/                 buttons, cards, dialogs, options sheet, loader
│   └── app_info.dart            version, privacy copy
├── features/<feature>/
│   ├── domain/                  entities, repository contracts, use cases
│   │                            — pure Dart, no Flutter imports
│   ├── data/                    models (JSON codecs), datasources, repository
│   │                            implementations — the only place packages live
│   └── presentation/            screens, widgets, Riverpod providers
├── routes/app_router.dart
└── injection/service_locator.dart
```

Features: `library`, `source_selection`, `editor`, `templates`, `export`,
`voice_input`, `smart_font_matching`, `settings`.

### Rules the code follows

- **Domain is Flutter-free.** Colour is an ARGB `int`, alignment and shadow
  are domain enums, geometry is plain `double`. No `Color`, no `Offset`.
- **Use cases are thin and single-purpose**, `const` constructors, one
  `call()`. 37 of them, every one registered in GetIt and resolved through
  `sl<T>()`.
- **Data layer owns every third-party package.** `printing`, `hive`,
  `file_picker`, `speech_to_text`, `image`, `pdf`, `dart:io` appear nowhere
  else.
- **Riverpod for state, GetIt for wiring.** Notifiers resolve use cases from
  `sl` and hold no business rules.

### Cross-feature dependencies (deliberate, three of them)

1. `library/domain` imports the editor's `TextElement` and
   `InvitationSourceFile` — a saved invitation *is* an editor document at
   rest; duplicating those shapes would guarantee they drift.
2. `templates/data` reuses `InvitationProjectModel`'s element codec — a
   template holds the same text boxes; two encoders would be two places to
   update.
3. `export/data` imports the editor's `TextElementStyle` extension — export
   must render text through the *same* mapper as the canvas, or printed
   output would not match the screen.

## Key design decisions

**Text geometry is normalised to the page.** `x`, `y`, `width`, `height` are
fractions of the page; `fontSize` is a fraction of page height;
`letterSpacing` is a fraction of font size. A layout is therefore identical
across screen sizes, survives zooming, and multiplies straight onto PDF point
sizes. This is the single decision most of the codebase rests on.

**Gesture maths uses global→page coordinate conversion, never
`DragUpdateDetails.delta`.** Inside a zoomed `InteractiveViewer` and a rotated
`Transform`, a raw delta is in the wrong frame: drags would run at the wrong
speed when zoomed and along the wrong axes when rotated. Resize becomes "how
much further from the centre did the finger move", rotate becomes "how much
did its bearing change" — both correct at any zoom and rotation.

**Hive stores JSON strings, not generated TypeAdapters.** Adapters need
`build_runner`; JSON keeps storage inspectable and versioned by an integer we
control. Every field is read through a total helper that supplies a default,
so a record written by an older build loads instead of throwing.

**Records store file names, never absolute paths.** Container paths change
between installs, so a persisted absolute path is a slow-acting bug —
the library would still list an invitation whose artwork had silently
vanished. `AppPaths` rebuilds paths at read time.

**Uploaded artwork is copied into app storage on save.** `file_picker` returns
paths in an OS cache the system may purge.

**Export re-renders offscreen at ~200dpi rather than screenshotting the
canvas.** A screenshot caps output at the phone's display resolution, which
prints soft. The PDF holds one full-page image rather than PDF text, because
each bundled font would need embedding and any missing font would silently
substitute. Trade-off: PDF text is not selectable.

**The formatting panel is in-layout, not a modal sheet**, so the text being
restyled stays visible — live preview requires it.

**The selection toolbar sits below the canvas**, not floating above the box as
the spec sketches. A floating bar would scale with canvas zoom, rotate with a
rotated box, and clip near the page edge.

**Deleting text uses an undo snackbar; deleting an invitation or template uses
a confirmation dialog.** Exactly the split the UX spec asks for.

**Smart Font Matching measures, it does not identify.** It reads dominant ink
colour, the spread of horizontal stroke run-lengths, and ink density, mapping
those onto four coarse style classes with a stated confidence. Identifying an
actual typeface needs OCR plus a font database. Confidence is worded ("a close
match") rather than given as a false percentage, and a low-confidence reading
renders nothing at all.

**Voice recognition forces `onDevice: true`.** With no INTERNET permission a
network recogniser would fail, so this converts a confusing mid-dictation
failure into a clear "not available on this phone" before listening starts.

## Offline guarantee

- No INTERNET permission in the release manifest. Debug and profile variants
  add it, because `flutter run` needs it for hot reload.
- `AppFonts.configureOffline()` disables `google_fonts` runtime fetching
  before any font resolves.
- No analytics, ads or networking package anywhere in `pubspec.yaml`.

## Known limitations

1. **Never compiled.** See "First build".
2. **Font files absent.** All 12 catalogue fonts fall back to the bundled
   serif until `.ttf` files are placed in `google_fonts/` — see the README
   there. No code change needed. Also caps PDF text fidelity.
3. **No bundled starter templates.** The UX spec lists ready-made
   wedding/birthday designs; that artwork does not exist. User-saved templates
   work fully and a blank-card tile is always present.
4. **No onboarding slides.** Section 3 of the UX spec (three first-launch
   slides) is not implemented.
5. **No "Open" button after export.** Needs a package like `open_filex`, which
   is not in the architecture's dependency list. Print and Share cover it.
6. **`AppInfo.version` is hand-maintained** against `pubspec.yaml`.
7. **PDF text is not selectable** — consequence of the render-to-image
   decision above.
8. **Editor top bar has no undo/redo or page settings**; the spec lists them
   under "Menu".
9. **On-device speech depends on the handset.** Some Androids ship no offline
   recogniser; those users get the fallback message and type instead.
10. **No tests.** `test/` contains only directory placeholders.
11. **Android only.** No `web/` or `ios/`. Web would not compile as-is: the
    storage and export layers use `dart:io` and `path_provider`.
12. **`applicationId` is `com.example.invitation_editor`** and release builds
    are signed with the debug key. Both must change before any store release.

## Verification performed

No compiler, so these were checked by static analysis over all 123 Dart
files. All pass as of the latest commit:

- Every relative import resolves; every `package:` import is declared
- No unused imports; no dead code
- Balanced delimiters
- Every `AppColors` / `AppDimensions` / `AppTextStyles` / `AppInfo` reference
  exists
- No unguarded `num.clamp()` feeding a `double` or `int` parameter
- No version-fragile APIs (`ref.mounted`, typed initialising formals)
- 37 use cases and 13 repositories registered in GetIt *and* resolved
- 14 Riverpod providers, each reachable from a screen
- Every pushed route declared; no orphan routes
- Every asset directory declared in `pubspec.yaml` exists and is non-empty
- Android XML well-formed; every `@style`/`@color`/`@drawable`/`@mipmap`
  reference resolves; Kotlin package matches the Gradle namespace
- Domain layer maths (clamps, centre preservation, aspect ratio, stacking
  order, delete/undo index restoration) checked by porting it and testing the
  invariants

## CI

`.github/workflows/build-invitation-editor.yml` builds the APK on GitHub's
runners, which have the network access the development environment lacked. On
success it publishes to a rolling `app-preview` release so the download URL
stays constant. On failure the job log carries the compiler output.
